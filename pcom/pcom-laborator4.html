02

De ce nu ajunge Ethernet?

Până acum am trimis date între dispozitive legate direct. Acum vrem să ajungem la dispozitive din alte rețele. În Londra sunt trei calculatoare și un router pe o rețea Ethernet; la fel în București. Routerele sunt legate între ele prin PPP. Host-ul A din Londra vrea să-i trimită ceva lui B, din București.

Ideea: la fiecare legătură, cadrul de nivel 2 se schimbă (Ethernet, apoi PPP, apoi iar Ethernet, cu alte adrese MAC). Datagrama IP din interior rămâne aceeași de la A la B: adresa IP destinație nu se schimbă. Routerele citesc adresa IP și decid pe unde trimit mai departe.

03

Antetul Ethernet, în C

În laborator lucrăm cu pachete reale din Internet: Ethernet și IP. Cadrele Ethernet le primim ca payload de la implementarea fizică. CRC-ul îl calculează placa de rețea, în hardware, așa că nu apare în antet.

<net/ethernet.h>
struct ether_header {
    uint8_t  ether_dhost[6];  /* MAC destinație, octeții 0–5  */
    uint8_t  ether_shost[6];  /* MAC sursă,      octeții 6–11 */
    uint16_t ether_type;      /* octeții 12–13, network order */
};

04

Antetul IPv4

IP permite dispozitivelor din rețele diferite să schimbe date prin intermediul routerelor. În laborator ne interesează doar trei câmpuri, colorate mai jos: TTL, checksum și adresa destinație. Apasă pe un câmp.

<netinet/ip.h>
struct iphdr {
    uint8_t  ihl:4, version:4;  /* 4 biți fiecare (ordinea e inversată pe little endian) */
    uint8_t  tos;
    uint16_t tot_len;
    uint16_t id;
    uint16_t frag_off;
    uint8_t  ttl;               /* îl decrementăm, ca să nu existe bucle infinite */
    uint8_t  protocol;
    uint16_t check;             /* îl recalculăm, pentru că am schimbat TTL-ul */
    uint32_t saddr;
    uint32_t daddr;             /* destinația pachetului */
};
05

Adrese, prefixe, măști

O adresă IP, cum e 10.20.30.40, are 32 de biți (în C, un uint32_t). Adresele sunt grupate în blocuri numite rețele, identificate printr-un prefix și o mască. Rețeaua din București, 10.20.30.0/24, are masca 255.255.255.0: /24 = numărul de biți de 1 ai măștii, de la stânga la dreapta. Prefixul se obține cu un AND pe biți: ip & mask.

06

Checksum-ul IP

Checksum-ul acoperă doar antetul: e complementul față de 1 al sumei tuturor cuvintelor de 16 biți din antet. Când routerul scade TTL-ul, antetul se schimbă, deci și checksum-ul trebuie refăcut. Mai jos e antetul unui ping de la host0 la host3. Mută TTL-ul și apasă pe router.

checksum-ul complet
/* întoarce checksum-ul în host order */
uint16_t ip_checksum(const void *hdr, size_t len)
{
    const uint8_t *b = hdr;
    uint32_t sum = 0;

    for (size_t i = 0; i + 1 < len; i += 2)
        sum += (b[i] << 8) | b[i + 1];   /* cuvinte big endian */
    if (len & 1)
        sum += b[len - 1] << 8;
    while (sum >> 16)                      /* transportul se adună */
        sum = (sum & 0xFFFF) + (sum >> 16); /* înapoi la capăt */
    return ~sum;
}

/* verificare: pe un antet corect, rezultatul e 0 */
if (ip_checksum(ip, sizeof(struct iphdr)) != 0)
    continue;                              /* aruncăm pachetul */

/* după ce schimbăm TTL-ul */
ip->check = 0;
ip->check = htons(ip_checksum(ip, sizeof(struct iphdr)));

Pentru că se schimbă doar TTL-ul, checksum-ul se poate actualiza incremental, fără să refaci toată suma (RFC 1624). Notații: HC = checksum-ul vechi, m = cuvântul de 16 biți vechi (TTL și protocol), m' = cuvântul nou.

HC' = ~(~HC + ~m + m')adunare în complement față de 1: transportul se adună înapoi

Formula din laborator scrie aceeași idee direct în C, cu un - 1 la final. Am testat-o pe un milion de antete aleatoare: în 16 cazuri a dat 0xFFFF acolo unde recalcularea completă dă 0x0000. Pentru un antet de 20 de octeți, cel mai simplu e să recalculezi tot.

    Longest Prefix Match

    Tabela de rutare are patru coloane: prefix, next hop, mască, interfață. O populează algoritmii de rutare (nu fac parte din PCom). Pentru o adresă destinație, routerul caută intrările pentru care (dest & mask) == prefix și o alege pe cea mai specifică: masca cea mai lungă.     LPM în C

    Varianta simplă, O(n): sortezi tabela o singură dată, descrescător după mască (apoi după prefix), și parcurgi de sus în jos. Primul rând care se potrivește e cel mai specific. Tabela e în network order: pentru comparații, trece valorile în host order cu ntohl.

    router.c (câmpurile intrării: verifică route_table_entry în lib.h)
    int cmp_route(const void *a, const void *b)
{
    const struct route_table_entry *x = a, *y = b;
    uint32_t mx = ntohl(x->mask), my = ntohl(y->mask);

    if (mx != my)
        return mx < my ? 1 : -1;          /* masca mai lungă întâi */
    uint32_t px = ntohl(x->prefix), py = ntohl(y->prefix);
    return px < py ? 1 : (px > py ? -1 : 0);
}

/* o singură dată, la pornire */
qsort(rtable, rtable_size, sizeof(struct route_table_entry), cmp_route);

struct route_table_entry *get_best_route(uint32_t ip_dest)
{
    for (int i = 0; i < rtable_size; i++)
        if ((ip_dest & rtable[i].mask) == rtable[i].prefix)
            return &rtable[i];             /* primul match = cel mai specific */
    return NULL;                           /* nicio rută: aruncăm pachetul */
}

    Față de fragmentul din laborator: comparația folosește rtable[i].mask, masca intrării curente (în fragment apare un mask care nu e definit nicăieri). Sortarea trebuie făcută întâi după mască: dacă sortezi întâi după prefix, primul match nu mai e neapărat cel mai specific. AND-ul pe biți merge direct în network order. Pentru o căutare mai rapidă decât O(n), poți folosi o trie pe biții adresei.

    Capcane

    ✗ compari în network order

    Măștile și prefixele din tabelă sunt în network order. Pentru < și >, treci-le prin ntohl. La fel ether_type: ntohs(eth->ether_type) == ETHERTYPE_IP. Doar == și AND-ul pe biți merg direct, fără conversie.

    ✗ TTL scăzut sub 1

    Verifică TTL-ul înainte să-l scazi: un uint8_t cu valoarea 0, scăzut, devine 255 și pachetul trăiește încă 255 de hop-uri.

    ✗ checksum peste câmpul vechi

    Când recalculezi, pune întâi ip->check = 0. Altfel calculezi suma cu tot cu valoarea veche.

    ✗ MAC-ul destinației finale

    În antetul Ethernet pui MAC-ul next hop-ului, nu al destinației din antetul IP. Destinația IP rămâne aceeași; adresele MAC se schimbă la fiecare hop.

    ✗ sortezi la fiecare pachet

    qsort o singură dată, la pornire. Apoi doar parcurgi tabela.

    ✗ sortezi după prefix

    Primul criteriu e masca. Altfel 192.168.0.0/16 poate ajunge înaintea lui 192.168.0.0/24.

    ✗ câte adrese are un /24?

    De la .0 la .255 sunt 256 de adrese, nu 255. Prima (rețeaua) și ultima (broadcast) sunt rezervate, deci rămân 254 pentru dispozitive.
